NEW / UPDATED FINDINGS (most severe first)
=====================================================================

[R1] SEVERITY: critical | NEW (this is the running FastAPI stack)
  FILE: app/detector.py:360 + app/main.py:116-129,631-632 + web/index.html:404
  ISSUE: E-STOP does not stop the rover while follow mode is active. The follow
    control loop re-arms motion within ~100 ms of every e-stop.
  EVIDENCE:
    - main.py trigger_estop(): sets self._estop = True and zeros the target.
    - main.py set_drive() (line 120): unconditionally does `self._estop = False`.
    - detector.py BoxFollower._loop writes `self.motor_target.set_drive(vx, 0.0, omega)`
      every INFERENCE_HZ tick (=10 Hz, line 360) whenever a target is seen.
    - main.py ws handler `elif t == "estop": target.trigger_estop()` does NOT
      disable the follower.
    - web/index.html estop click (line 404) sends only {type:"estop"} — it does
      not send set_follow_mode:null and does not clearAllActions().
  FAILURE MODE: Operator is dog/person-following, rover is driving toward the
    subject, operator slams E-STOP. trigger_estop zeros the target for one motor
    tick; the follower thread's next tick (<=100 ms) calls set_drive() with a
    fresh non-zero command, which clears the _estop latch, and the rover resumes
    pursuit. E-STOP is effectively a ~100 ms tap, not a stop.
  FIX: E-stop must latch independently of set_drive. Options: (a) trigger_estop
    also disables the follower (follower.set_enabled(False)); (b) make _estop a
    sticky latch that set_drive cannot clear — require an explicit estop_clear
    message; (c) have BoxFollower check an estop flag before every set_drive.
    Recommend (a)+(b) together, and have the client estop handler also send
    set_follow_mode:null and clearAllActions().

[R2] SEVERITY: high | NEW
  FILE: app/detector.py:355-365 + app/main.py:583-596
  ISSUE: No reliable manual override while following — the joystick and the
    follower race on the shared MotorTarget with last-writer-wins, and the
    follower overwrites manual input every ~100 ms.
  EVIDENCE: main.py comments claim "Non-zero input still wins -> instant manual
    override" (line 590-591) and ignores only *idle* (all-zero) joystick
    heartbeats while follow is enabled. But BoxFollower._loop unconditionally
    calls set_drive at 10 Hz (detector.py:360/365); there is no teleop-priority
    window and nothing disables the follower on manual input. A manual command
    written at T is stomped by the follower's command at T+<=100 ms.
  FAILURE MODE: Subject or rover drifts toward a hazard; operator pushes the
    stick to steer away; the rover obeys for ~100 ms then the follower resumes
    its own heading. To actually take control the operator must first toggle
    follow off. This is a regression vs the ROS person_follower, which had an
    explicit teleop-override that disabled following on external cmd_vel.
  FIX: Give manual input precedence: on any non-zero joystick command while
    following, either disable the follower (mirror the ROS teleop-override) or
    set a short "manual hold" window during which the follower yields (skips its
    set_drive). Document which wins.

[R3] SEVERITY: medium | NEW (persists from pass-1 #1, manual-drive vector)
  FILE: app/main.py:116-120 + web/index.html:404,543
  ISSUE: In manual mode the e-stop latch is also cleared by a held/stuck control,
    because the client streams drive at 20 Hz and e-stop does not clearAllActions.
  EVIDENCE: setInterval(sendDriveNow, 50) (index.html:543) sends drive every
    50 ms; a physically held direction button keeps a non-zero command in
    activeActions; the estop handler (line 404) does not clear activeActions, so
    the next 50 ms frame calls set_drive (non-zero) and clears _estop.
  FAILURE MODE: A touch/pointer sticks or a button is held when E-STOP is
    pressed; rover halts for one tick then re-arms at the held velocity.
  FIX: Same latch fix as R1 (sticky e-stop), plus clearAllActions() in the
    client estop handler so no held action survives the stop.

[R4] SEVERITY: medium | NEW (safety behavior of edge-reverse)
  FILE: app/detector.py:80-88,427-437
  ISSUE: The new edge-safety reverse drives the rover BACKWARD with no rear
    sensing. When the subject's bbox is clipped at the top/bottom frame edge
    (subject too close/tall), the loop commands vx = -EDGE_REVERSE_SPEED.
  EVIDENCE: `if target["edge_clipped"]: vx = -EDGE_REVERSE_SPEED` (line 431);
    edge_clipped = y1<margin OR y2>h-margin (line 390). Reverse is gentle
    (0.20 * MAX_LINEAR = 0.1 m/s) but continuous while clipped.
  FAILURE MODE: Subject walks up to the rover; rover backs away to keep the whole
    body framed, with zero awareness of what is behind it — backs into a wall,
    a ledge/curb, or a person standing behind. The rover has no rear camera or
    proximity sensor to gate this motion.
  FIX: Bound the reverse (time-limit or total-distance-limit per clip event),
    and/or require the subject to be centered before reversing, and document that
    the rover has no rear obstacle detection. Consider stop-instead-of-reverse as
    the default and make reverse opt-in.

[R5] SEVERITY: low-medium | NEW (unauthenticated control surface, now larger)
  FILE: app/main.py:551-571 (POST /api/video/config), 485-540 (/ws/video), 574 (/ws)
  ISSUE: The new HTTP/WS endpoints are unauthenticated (like the rest of the app)
    and POST /api/video/config accepts width/height with no sane bounds.
  EVIDENCE: set_video_config passes payload width/height straight into
    streamer.reconfigure; streamer only clamps fps>=1 and bitrate>=64
    (streamer.py:195-198) — width/height get int() with no lower/upper bound.
    A width<=0 makes cv2.resize raise every feeder tick and ffmpeg fail to start
    (-video_size 0x480), killing the video feed and spinning warnings.
  FAILURE MODE: Any device on the LAN / Tailscale / LTE-failover path can POST a
    zero/negative/huge resolution and DoS the camera stream, or open many /ws and
    /ws/video sockets (no client cap). Combined with pass-1 #5 (path traversal on
    the ROS dashboard's :8080) the overall unauthenticated surface is broad.
  FIX: Validate width/height to a small allow-list or clamp to e.g. [160,1920] x
    [120,1080] and require even dimensions; consider a shared secret / same-LAN
    check for state-changing endpoints (config, shutdown, drive).

[R6] SEVERITY: low | NEW (concurrency)
  FILE: app/detector.py:291-302,316-331 (set_enabled/_start) via main.py:610,614 run_in_executor
  ISSUE: set_enabled is dispatched to the default thread-pool executor from the
    WS loop; two rapid follow toggles can run set_enabled(True) and (False) on
    different pool threads concurrently, racing on _enabled/_thread/_yolo with no
    lock around start/stop (only the status fields are lock-guarded).
  FAILURE MODE: Fast double-tap of the DOG/PERSON buttons during the ~3 s Hailo
    init could start a second loop thread or tear down _yolo while _start reads
    it. Low likelihood on a single-user dashboard; worst case a follower thread
    left running or an init exception.
  FIX: Guard _start/_stop/close and the _enabled transition with a dedicated
    lifecycle lock; ignore toggles while a transition is in flight.

=====================================================================
SUMMARY
=====================================================================
The single most important issue is R1: with the new dog/person follower, E-STOP
does not stop a following rover — the follow loop clears the e-stop latch within
~100 ms via the shared set_drive path. R2 is the companion problem: there is no
reliable manual override while following, so the operator cannot quickly steer
out of trouble without first toggling follow off. Both are new with the follower
rewrite and both are the running FastAPI stack (app/), not the legacy ROS nodes.
Fix R1 first (make e-stop a sticky latch AND have it disable the follower), then
R2 (manual-input precedence), then R4 (bounded/gated reverse, since the rover
backs up blind). The streamer (app/streamer.py) is otherwise solid — good process
isolation, slow-client detach, and init-segment handling; its only issues are the
unbounded config input (R5). All 11 pass-1 ROS-stack findings remain open.

    systemd/ but was not in the installed-unit list; brain_launcher launches
    brains by brain.yaml start_command. R1-R6 assume the app/ stack is live (it
    is what rover-uvicorn + the docstrings target). Confirm with:
    `systemctl is-enabled rover-uvicorn` and `pgrep -af uvicorn`.
(b) R1/R2/R3 verified by code reading; not exercised on hardware (review is

(c) R4 framing math: edge-clip reverse mainly engages when the subject is close
