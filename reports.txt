FINDINGS (most severe first):

[#1] SEVERITY: critical | NEW
  FILE: app/main.py:108-112 (+ web/index.html:333,337)
  ISSUE: E-stop in the FastAPI stack (the one systemd actually runs via rover-uvicorn.service) is cleared by the very next drive message, and the web client streams drive messages unconditionally at 20 Hz — so E-STOP stops the rover for at most ~50 ms.
  EVIDENCE: `def set_drive(...): ... self._estop = False` (main.py:112); client: `setInterval(sendDriveNow, 50)` (index.html:337) sends {type:"drive",...} every 50 ms regardless of input, and the estop button handler (`send({ type: "estop" })`, index.html:333) does NOT clear activeActions.
  FAILURE MODE: A drive button is held or stuck (touchscreen glitch, multi-touch pointer capture); user slams E-STOP; robot halts for one motor tick, then the next 50 ms drive frame re-arms motion at the held velocity. The docstring's "latches until the next drive command" design is nullified by the unconditional 20 Hz stream.
  FIX: On e-stop, either (a) require an explicit {"type":"estop_clear"} before set_drive un-latches (ignore drive while _estop is set), and/or (b) in the client, clear activeActions and stop the send interval until the user re-touches a control.

[#2] SEVERITY: high | NEW
  FILE: rover2_dashboard/rover2_dashboard/web_dashboard.py:733-751 (+ rover2_vision/rover2_vision/person_follower.py:684-691)
  ISSUE: The ROS dashboard's "emergency_stop" only publishes zero Twists, which the person follower explicitly ignores as an override — so an actively-following robot resumes motion on the next camera frame.
  EVIDENCE: dashboard: `for _ in range(5): self.cmd_vel_pub.publish(twist)` (all zeros); follower: `is_nonzero = (abs(msg.linear.x) > 0.01 or ...)` then `if is_nonzero: self.last_external_cmd_time = now` — zero commands never set the override timestamp.
  FAILURE MODE: Person-following is enabled, robot is driving toward someone; operator hits the dashboard E-STOP; five zero Twists go out, follower's next image_callback/safety_check publishes a fresh nonzero cmd_vel <=100 ms later and the robot keeps moving.
  FIX: emergency_stop() should first call the /person_follower/disable (or reset) service, then publish zeros; alternatively treat any external cmd_vel (including zeros) as an override in the follower.

[#3] SEVERITY: high | NEW
  FILE: rover2_vision/rover2_vision/person_follower.py:769-770 (vs. 841 and 1292-1302)
  ISSUE: image_callback returns before updating the stall-watchdog timestamp whenever following is disabled, so in detection-only mode the watchdog either endlessly tears down/reinits Hailo (if following was ever enabled) or is completely inert (if it never was).
  EVIDENCE: `if not self.following_enabled: return` (line 769) sits above `self.last_image_processed_time = time.time()` (line 841); watchdog: `if elapsed > self.watchdog_timeout: ... self._cleanup_hailo(); self._init_hailo()` (1298-1302).
  FAILURE MODE: User enables following, then disables it but leaves detection on to watch bounding boxes. Frames process fine, but last_image_processed_time goes stale; 5 s later the watchdog "recovers" by reloading the Hailo engine (2-3 s stall), and repeats forever — CPU/thermal churn on a passively-cooled Pi already running 75-80 C, plus periodic detection blackouts.
  FIX: Move the last_image_processed_time update to immediately after inference succeeds (right after line 707), before any following-related early returns.

[#4] SEVERITY: medium | NEW
  FILE: rover2_vision/rover2_vision/person_follower.py:1300-1301 (with 261-265, 466-471, 1326)
  ISSUE: The watchdog can destroy the Hailo pipeline while image_callback is concurrently inside infer() — they're in different callback groups on a MultiThreadedExecutor with no lock guarding the Hailo handles.
  EVIDENCE: watchdog (timer_cb_group) calls `self._cleanup_hailo(); self._init_hailo()`; image path (subscription_cb_group) uses `self.infer_pipeline.infer(input_dict)` (line 953). MutuallyExclusive groups only serialize within a group, not across groups.
  FAILURE MODE: Inference genuinely stalls or runs long; watchdog fires and __exit__s the vstreams under an in-flight native infer() call — best case an exception, worst case a segfault in the Hailo SDK taking the whole node down (respawn=True masks it but the robot coasts/stops mid-follow).
  FIX: Guard run_inference, _init_hailo, and _cleanup_hailo with a shared threading.Lock, or move the watchdog into subscription_cb_group so teardown serializes with the image callback.

[#5] SEVERITY: medium | NEW
  FILE: rover2_dashboard/rover2_dashboard/web_dashboard.py:761-768
  ISSUE: The custom translate_path override drops SimpleHTTPRequestHandler's ".."-sanitization, giving directory traversal on the HTTP server bound to 0.0.0.0:8080.
  EVIDENCE: `relative_path = path.lstrip('/'); return str(self.static_dir / relative_path)` — no normpath/containment check (the stock implementation it replaces filters ".." components).
  FAILURE MODE: Any device on the LAN/Tailscale (and via the LTE failover path) requests GET /../../../../home/andrewmeckley/.ssh/id_ed25519 with a raw (non-normalizing) client and reads arbitrary files as the rover user. Same server also exposes unauthenticated shutdown/reboot/teleop over the :8081 WebSocket — worth noting even if accepted for a hobby network.
  FIX: Resolve the joined path and verify Path(...).resolve().is_relative_to(self.static_dir.resolve()) before serving; return 403/404 otherwise.

[#6] SEVERITY: medium | NEW
  FILE: rover2_bringup/launch/rover2.launch.py:203-210
  ISSUE: The launch starts joy_node but nothing in the rover2 stack converts /joy to /cmd_vel — physical gamepad teleop (and thus the controller as a manual override/stop channel) is nonfunctional.
  EVIDENCE: Only `Node(package='joy', executable='joy_node', ...)`; rover2_hardware/setup.py entry points are berry_imu_driver, hiwonder_driver, mecanum_kinematics, battery_monitor, fix_to_nmea — no stadia_teleop, and no teleop_twist_joy anywhere in rover2 packages (grep confirmed).
  FAILURE MODE: Person following misbehaves outdoors; operator reaches for the Stadia controller expecting the documented "teleop override" — nothing happens; only the web dashboard (WiFi/LTE-dependent) can intervene.
  FIX: Add teleop_twist_joy (or port stadia_teleop.py from rover1) to the launch, or delete joy_node and document that the web UI is the sole teleop path. Marked verified for "not in this repo's launch"; unverified whether a teleop node is run out-of-band.

[#7] SEVERITY: medium | NEW
  FILE: rover2_dashboard/rover2_dashboard/web_dashboard.py:319-327 (+ 260-268, 839)
  ISSUE: Blocking subprocess.run calls (nmcli up to 2 s, vcgencmd) execute on the node's single-threaded executor, starving the 20 Hz publish_pending_teleop timer that forwards web teleop cmd_vel.
  EVIDENCE: `subprocess.run(['nmcli', ..., 'dev', 'wifi', 'list'], ..., timeout=2.0)` in a 3 s timer; `rclpy.spin(dashboard)` (line 839) is a single-threaded executor, so all callbacks serialize.
  FAILURE MODE: nmcli dev wifi list triggers a scan taking 0.5-2 s; during it no queued cmd_vel is published, and the hiwonder 0.5 s watchdog stops the motors — periodic hitching every 3 s while driving from the web dashboard (compounds the known WS-backlog jerkiness).
  FIX: Run power/WiFi checks in a background thread that posts results, or use a MultiThreadedExecutor with the blocking timers in their own callback group.

[#9] SEVERITY: low | NEW

  ISSUE: enable_person_follower has contradictory defaults — LaunchConfiguration(..., default='false') but DeclareLaunchArgument(..., default_value='true'); the declared 'true' wins, so the follower node auto-starts despite line 19 suggesting otherwise.

[#10] SEVERITY: low | NEW
  FILE: rover2_hardware/rover2_hardware/berry_imu_driver.py:31, 55, 78-93, 110-112
  ISSUE: last_time is captured before the ~10-15 s blocking gyro calibration (1000 x 10 ms + I2C reads), so the first timer_callback integrates gyro rates over a giant dt.
  EVIDENCE: `self.last_time = self.get_clock().now()` (line 31) precedes `self.calibrate_gyro(...)` (line 55); first callback: `dt = (current_time - self.last_time).nanoseconds / 1e9` then `self.yaw += gz * dt` (148).
  FAILURE MODE: Residual bias/noise x ~15 s produces an initial yaw/roll/pitch jump the EKF ingests at startup; roll/pitch recover via the complementary filter, yaw offset persists (yaw is integration-only).
  FIX: Reset self.last_time = self.get_clock().now() right before creating the timer (after calibration), or clamp dt in the callback.

[#11] SEVERITY: low | NEW
  FILE: brain_launcher.py:202-206
  ISSUE: subprocess.run(brain['start_command'], shell=True) blocks the Tk mainloop for the brain's entire lifetime — the launcher UI (Escape/Exit) is dead while a brain runs, and there's no handle to stop the child.
  EVIDENCE: `result = subprocess.run(brain['start_command'], shell=True, cwd=brain['path'])` called directly from the button handler.
  FAILURE MODE: Brain hangs; touchscreen shows nothing interactive (window withdrawn, loop blocked); only recourse is killing the service — mitigated by systemd cgroup kill and launch_pack_robot.sh's pgrep duplicate guard, but there is no in-UI stop/return path.
  FIX: Use subprocess.Popen with a stored handle, poll via root.after(), and add a "Stop brain" control that terminates the process group.

KNOWN-ISSUE CROSS-CHECK: bug_log.md's critical "watchdog missing / motor latching" item is resolved in the current hiwonder_driver.py (watchdog at lines 97-104 verified present, polarity params present); rover2_audit_findings.md and refactor1.md are planning docs and list none of the findings above — all 12 findings are NEW.

SUMMARY: The drive chain fundamentals are in good shape — kinematics math checks out (IK/FK are the standard mecanum forms, polarity handling matches the verified wiring notes), the motor driver has a real 0.5 s watchdog, and the new FastAPI stack (app/) is cleanly architected. The biggest risk is that both stacks' emergency-stop paths fail exactly when needed: the FastAPI e-stop is un-latched within 50 ms by the client's unconditional drive stream (#1), and the ROS dashboard e-stop can't stop an actively-following robot (#2). Fix #1 and #2 first (both are small, targeted changes), then the follower watchdog timestamp bug (#3), which quietly burns CPU and thermal headroom on a Pi that's already soft-throttled.
