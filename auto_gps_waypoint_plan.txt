======================================================================
0. BOTTOM LINE
======================================================================

The rover already has about 70 percent of a real waypoint follower:

  * RTK position (ZED-F9R + Iowa DOT RTN) written to a status file by
    scripts/ntrip_rtk.py; the receiver solves at 1 Hz today (measured),
    which v2 raises to 2 to 4 Hz with one configuration message
  * a safe motor layer (E-stop latch, 150 ms watchdog, manual override)
    on a Hiwonder board with working encoders (closed-loop speed mode is
    unconfirmed, see 1.1)
  * a pure-pursuit follower (app/nav.py) with sensible gates and phases,
    which has only ever run in simulation
  * surveyed paths (sidewalk spots 1 to 4, densified at 0.5 m) and a map
    page with START/STOP PATH and a live rover marker

The missing 30 percent is the same thing that made the year-ago run
painful: HEADING. The July follower takes heading from GPS course over
ground while moving and dead-reckons turns from the commanded yaw rate
(open loop, never calibrated, and about 20 to 40 percent optimistic by
my arithmetic in section 9). That cannot pivot 180 degrees accurately,
cannot hold a line when course-over-ground is noisy at 0.25 m/s, and
knows nothing while the rover is parked. The year-ago attempt used the
magnetometer on a steel chassis next to four brushed motors, which is
why it wandered. Neither approach anchors heading to a gyro.

The fix: a gyro-anchored heading estimator corrected continuously by RTK
(receiver course over ground plus track angle from position deltas). The
gyro is the ZED-F9R's own internal IMU: the recon found the BerryIMU
electrically absent, but the F9R is a sensor-fusion receiver with a
6-axis IMU inside, and its raw samples can be enabled on the USB link we
already use (UBX-ESF-RAW; integration manual UBX-20039643 section
3.2.7.6; the PDF is in the repo as "ZED-F9R ublox.pdf"). The receiver's
own fusion engine is NOT used: its automotive model never initializes
below 30 km/h, and the low-speed "robotic lawn mower" model needs wheel
ticks and RTK FIXED to calibrate (section 1.2). Everything else is
engineering on top of
code that already exists: a mission layer (once / ping-pong / loop with
turnarounds), waypoint-creation tooling on the rover, calibration of
speed and yaw rate, run logging, and a field protocol.

Six work packages (section 5). Realistic path to "sidewalk 1 -> 4 -> 1,
three times, hands off" is three to four field outings after the code is
on the rover, with the first outing being calibration only. One bench
session comes first and is decisive: enable UBX-ESF-RAW and read the
F9R's gyro for 60 s (WP0b, T1). If that works, the hardware is done. If
it does not, the fallback is remounting the BerryIMU (R1).

1.1 Live stack (what actually turns the wheels)

  systemd/rover-uvicorn.service runs FastAPI app/main.py on :8080 from
  ~/code/rover1-venv, working directory ~/ros2_ws/src/rover1 on the Pi.
  The ROS 2 packages (rover1_*, rover2_*, Nav2, EKF, patrol) are legacy
  reference code; they are not what drives today.

  app/main.py MotorTarget
    normalized (vx, vy, omega) in [-1, 1]; power slider scale 0.05..1.0;
    E-stop sticky latch; 0.5 s manual-hold priority over source="follow";
    150 ms stale-target watchdog. Motor thread at 50 Hz.
  app/kinematics.py
    cartesian_to_wheels: lx=0.10, ly=0.08, r=0.04, MAX_RPM=200,
    ROTATION_SCALE=2.0. Geometry constants are legacy guesses, not
    measurements (see 9.1).
  app/motors.py
    one 4-byte I2C block write to registers 0x33..0x36 (51..54), polarity
    (-1, +1, +1, -1) for (FL, FR, RL, RR).

  Finding: per the Hiwonder manual (iCloud "Rover PurePursuit/Encoder
  Motor Driver Module User Manual.pdf", register table, decimal values
  printed with an 0x prefix) register 51 is MOTOR_FIXED_SPEED_ADDR, which
  the manual labels closed-loop; register 31 is the open-loop PWM
  register. The unit is not stated; the old ROS driver's comment says
  "pulses per 10 ms". The manual's sample code writes the motor type
  (register 20 = 0x14, value 3 for JGB37-520) and encoder polarity
  (register 21 = 0x15) before using fixed-speed mode; nothing in this
  repo ever writes them.
  Recon 2026-10-31: register 0x14 reads 0 and 0x15 reads 0. In the
  manual's defines, 0 is MOTOR_TYPE_WITHOUT_ENCODER. So the board does
  not know the pulses per revolution of these motors, and whether it is
  actually closing a speed loop on register 51 in that state is
  undetermined (the encoders do count: the 0x3C totals are nonzero and
  frozen while still). v1's claim "closed-loop all along" is withdrawn
  until WP0b's bench test settles it. Teleop works either way; autonomy
  cares because a true speed loop gives repeatable straight lines and
  pivots regardless of battery voltage and grass.

  Encoders: register 0x3C returns 4 x int32 totals (mapping and polarity
  in engineering_log.md section 1.2). Dec 2025 calibration: 12,618.75
  ticks per meter (3,845 ticks per wheel rev with the 97 mm wheel). Not
  used by the live stack. They are free odometry and stall detection.

1.2 GPS

  scripts/ntrip_rtk.py (rover-ntrip.service, user unit, system python3,
  no pyserial: raw os.read/termios on
  /dev/serial/by-id/usb-u-blox_AG_-_www.u-blox.com_u-blox_GNSS_receiver-if00)
    NTRIP client to Iowa DOT RTN, mountpoint MSM_IMAX (4 constellations),
    RTCM to the F9R over USB, honest GGA every 10 s, polls NAV-PVT and
    NAV-DOP every 0.5 s, writes $XDG_RUNTIME_DIR/rover-gps-status.json
    atomically: fix, sats, hacc_m, caster, lat, lon (1e-7 deg), alt,
    speed_mps, cog_deg (headMot), cog_acc_deg (headAcc). It already has a
    UBX frame parser (Receiver.pump), which v2 extends.

  Measured by the recon (docs/rover-state-2026-10-31/04*):
    * The file is rewritten every 0.55 s but lat/lon change at 1.02 Hz:
      the receiver's navigation rate is the 1 Hz default (integration
      manual 3.2.6.2). Nothing in the repo or the home dir sets CFG-RATE.
      Position latency today is therefore up to 1 s plus the poll, about
      25 cm of travel at 0.25 m/s. WP1 sets CFG-RATE-MEAS to 500 ms (2 Hz)
      and tries 250 ms (4 Hz) after checking CPU load; the manual gives no
      hard GNSS-only maximum, only "check the enabled output messages at
      higher rates". The 30 Hz figure applies to priority navigation
      mode, which needs calibrated fusion and does not apply here.
    * Only ONE outdoor session exists in the journal (2026-07-19; older
      entries rotated away). That evening: 10 FIXED stretches, 49 s in
      total, longest 17 s, at hAcc 0.02 to 0.03 m, all between 17:07 and
      17:11 while the spots were surveyed; FLOAT at 0.08 to 0.40 m in that
      window. From 17:38 (service restart, hAcc 64 m, so the receiver had
      been restarted or power cycled) through 18:20 the solution flapped
      FLOAT/NONE at hAcc 0.8 to 2.2 m and never reconverged. Four
      rover-ntrip starts and four rover-uvicorn starts fall in 17:38 to
      17:54. Lesson: a converged solution is fragile; do not restart
      services or power during an outing, and soak before driving.
    * v1's planning numbers ("FLOAT 0.12 to 0.20 m typical") came from
      the survey window only. Plan on FLOAT between 0.1 and 0.4 m on a
      good stretch, and on 1 to 2 m being possible for tens of minutes.
    * Not logged anywhere today: age of RTCM corrections, receiver
      variant and firmware (MON-VER), fusion status (ESF-STATUS). WP1
      adds all three.

  The receiver is more than a GPS. The integration manual in the repo
  ("ZED-F9R ublox.pdf" = UBX-20039643 R10) states:
    * 3.2.7.6: UBX-ESF-RAW outputs the internal IMU's raw accelerometer,
      gyroscope and temperature samples at the sensor's fixed sampling
      rate, enabled with the CFG-MSGOUT-UBX_ESF_RAW-* keys; enabling it
      does not disable fusion. Data types: 5 = z gyro, 13 = y gyro,
      14 = x gyro, in deg/s x 2^-12 as 24-bit signed; 16/17/18 = x/y/z
      specific force in m/s^2 x 2^-10; 12 = gyro temperature in 0.01 C.
    * 3.2.6.1: CFG-SFCORE-USE_SF turns fusion off; the receiver then
      outputs a GNSS-only solution and ESF-RAW keeps working.
    * 3.2.7.1.1 and the calibration tables: the default automotive fusion
      model needs 30 km/h to align the IMU mount, so on this rover the
      fusion engine stays in INITIALIZING and NAV-PVT is already
      GNSS-only. Good: no hidden dead-reckoning model is shaping the
      positions we steer by.
    * 3.2.2.2: the "robotic lawn mower" model (CFG-NAVSPG-DYNMODEL = 11,
      firmware HPS 1.21 or newer, so not on a -01B module) is a true
      low-speed differential-drive fusion with heading output, but it
      requires wheel ticks with polarity fed to the receiver, user-defined
      mount alignment, and RTK FIXED during calibration. Given 49 s of
      FIXED in the only logged evening, that is a stretch goal (R10), not
      the plan.
  Variant and firmware are unknown until MON-VER is read (WP0b).

  within 3 m of path start, pause on RTK loss (fault after 30 s mid-run,

  three starts from the phone at 17:57, 17:59 and 17:59:31, stopped by

======================================================================
2. WHY THE YEAR-AGO RUN WAS PAINFUL, AND WHAT IS DIFFERENT
======================================================================

Source: iCloud Drive "Rover PurePursuit" (single commit 2025-11-16;
drive.py 1,615 lines, pure_pursuit.py, mission_planner.py,
imu_fusion.py, rover_lite.py, ROOF_MOUNT_UPGRADE.md).

Root causes, in order of damage:

  1. Heading from the magnetometer (LIS3MDL) with a hand-made 4-point
     compass correction, later a 98/2 gyro/mag complementary filter.
     The notes record a 133 deg/s gyro offset and 28.6 deg heading
     standard deviation before the IMU was moved to the roof. A steel
     chassis, four brushed motors and their wiring make a magnetometer
     a poor heading reference at any mounting distance this rover can
     offer. The filter still trusted the magnetometer for the long term,
     so the long-term heading was wrong whenever the mag was wrong.
  2. Waypoint-to-waypoint control (not path-relative): sparse waypoints
     (2.5 m minimum spacing), capture radius 0.2..1.0 m, stop-and-turn
     above 45 deg error, constant 0.3 m/s with no slowdown. The rover
     cut corners, overshot captures and re-aimed, which reads as
     wandering.
  3. Position from NMEA GGA (lower precision formatting, about 1 Hz)
     rather than UBX NAV-PVT, with no latency compensation. (The current
     stack reads NAV-PVT at full precision but, per the recon, still at
     the receiver's 1 Hz default until WP1 raises it.)
  4. No calibration of motor units versus m/s or rad/s, commands clamped
     to +-50, and no run logs to diagnose any of the above.

What the old code got right and this plan keeps:

  * a mission state machine with endpoint detection, 180 deg pivot,
    direction flip, loop counting and estimated loop time
  * GPS and RTK quality gating with explicit stop reasons
  * manual waypoint marking with a GPS-quality check
  * a motion profiler (acceleration limiter)

What is different now: RTK at 2 to 40 cm when converged (and a logged
warning that it can sit at 1 to 2 m for half an hour), densified paths
with path-relative control (nearest point + carrot), a safe motor layer,
encoders that count, and a status-file interface that any process can
consume. Still missing, then and now: a trustworthy heading source and
measured calibration constants. Those are WP1 and WP4. The heading
source is now identified and already on the rover (the F9R's IMU).

======================================================================
3. TARGET BEHAVIOR AND DEFINITION OF DONE
======================================================================

Operator story: open /map on the phone, pick a saved path, choose a mode
(once, pingpong, loop) and a count, set cruise speed, press START. The
rover waits for RTK-grade accuracy, establishes heading, tracks the path
at cruise, slows into bends and the endpoint, stops within 0.3 m of the
end, then either finishes (once), pivots 180 deg and tracks the path
back (pingpong), or continues from the last point to the first (loop).
Repeats until the count is reached or STOP, E-stop, or a fault. The
operator can grab the D-pad at any time; the mission resumes about half
a second after release. Every run leaves a CSV log that can be replayed
offline and plotted on the satellite mosaic.

Acceptance tests (sidewalk path, RTK FLOAT or better):

  A1  Straight 10 m at 0.25 m/s: mean cross-track <= 0.15 m,
      max <= 0.30 m, stop error <= 0.30 m.
  A2  Pivot 180 deg on the gyro: final error <= 5 deg, done in <= 6 s,
      repeatable in both directions.
  A3  Sidewalk spot 1 -> 4 (19.3 m, two ~70 deg bends): max cross-track
      <= 0.40 m, arrival <= 0.30 m, no control-induced pauses (pauses
      caused by RTK loss are allowed and logged).
  A4  Pingpong 1 -> 4 -> 1, three times, hands off: all six legs
      complete, total time under 8 minutes, zero faults.
  A5  (stretch) Parcel boundary loop inside a 1 m geofence margin.

======================================================================
4. TARGET ARCHITECTURE
======================================================================

Processes on the rover (both user systemd units, as today):

  rover-ntrip.service   scripts/ntrip_rtk.py v2
      RTK corrections and caster etiquette unchanged. At startup, one
      UBX-CFG-VALSET to the RAM layer only (a power cycle reverts it):
      CFG-RATE-MEAS 500 ms (2 Hz, 250 ms later), CFG-RATE-NAV 1,
      CFG-MSGOUT-UBX_NAV_PVT_USB 1 (periodic instead of polled, poll kept
      as a fallback), CFG-MSGOUT-UBX_ESF_RAW_USB 1 (raw IMU stream),
      CFG-MSGOUT-UBX_ESF_STATUS_USB at 0.1 Hz (fusion mode, for the log).
      MON-VER polled once at startup and logged (variant, firmware).
      Status file written per NAV-PVT with seq and iTOW so consumers can
      tell a new sample from a re-read, plus rtcm_age_s, imu_rate_hz and
      imu_seq. Each ESF-RAW sample (host monotonic time, receiver sTtag,
      gx, gy, gz in deg/s, ax, ay, az in m/s^2, temp) is sent as one UDP
      datagram to 127.0.0.1:47101; loopback UDP is effectively lossless
      and keeps a 100 Hz-class stream out of the file system. USB CDC has
      bandwidth to spare (about 7 KB/s for ESF-RAW).
      Optional, decided on the bench: CFG-SFCORE-USE_SF 0 so the fusion
      engine can never engage; the manual says it stays in INITIALIZING
      on this rover anyway, so this is belt and braces [VERIFY whether it
      applies without a receiver restart; if not, leave it out].

  rover-uvicorn.service  app/
      app/gps.py       GpsSource: parses the status file, detects new
                       samples by seq, exposes sample + age + quality.
      app/imu.py       GyroSource with two backends behind one interface
                       (samples of t, gx, gy, gz, ax, ay, az, temp):
                       F9rEsfRaw (UDP listener on 127.0.0.1:47101, the
                       plan's default) and Lsm6dsl (smbus2, only if a
                       BerryIMU is remounted). Bias estimation while
                       stationary; yaw axis and sign from nav_params.
      app/heading.py   HeadingEstimator: gyro-integrated yaw (compass
                       sense) corrected by RTK observations: receiver
                       course over ground weighted by headAcc, and track
                       angle from position deltas over a minimum
                       baseline. Online gyro-bias estimate. Publishes
                       heading_deg, heading_valid, sigma, gyro_rate.
      app/paths.py     Path/waypoint model: load CSV, densify, reverse,
                       close, ENU projection, nearest/carrot/progress,
                       local curvature. Replaces the _Path class.
      app/mission.py   Mission state machine: legs, modes, counts,
                       turnaround, per-leg timeouts, run log file.
      app/nav.py v2    Tracking controller + the v1 safety gates.
      app/main.py      API additions (section 5 WP2/WP3), /telemetry
                       gains heading and mission fields.
      web/map.html     mission panel, MARK SPOT, tap-to-add waypoint,
                       BUILD PATH, path picker, leg/loop counters.

  scripts/             calib_gyro.py, imu_axes.py, calib_yaw.py,
                       calib_speed.py (field calibration, section 5 WP4)
  tools/               replay_nav.py (offline replay of a run log through
                       the controller), plot_run.py (Mac: track and
                       cross-track on the mosaic)
  tests/               sim_nav.py (kinematic sim: slip, GPS noise, rate,
                       latency, gyro bias) and unit tests for wrap math,
                       ENU, path ops, mission transitions.

Data flow:

  F9R (USB) -> ntrip_rtk.py -> status.json at 2 to 4 Hz -> GpsSource
  ntrip_rtk.py -> UDP 127.0.0.1:47101 at the IMU rate -> imu.py
  imu.py + GpsSource -> HeadingEstimator
  HeadingEstimator + GpsSource + Path -> nav controller (20 Hz)
     -> MotorTarget.set_drive(source="follow")
     -> motor thread 50 Hz -> kinematics -> Hiwonder register 51

    variant), 250 ms once MON-VER and the Pi load are known; periodic
    NAV-PVT with the poll kept as a fallback if no frame arrives for 2 s;
    ESF-RAW parsing (class 0x10 id 0x03: 4 reserved bytes, then 8-byte
    entries of a 32-bit data word with dataType in bits 24..29 and a
    24-bit signed value in bits 0..23, followed by a 32-bit sensor time
    tag); gyro in deg/s = value x 2^-12, accel in m/s^2 = value x 2^-10.
    One UDP datagram per sample to 127.0.0.1:47101. MON-VER once,
    ESF-STATUS fusionMode logged every 10 s, correction age logged
    (parse the receiver's own GGA field 13 if NMEA output is on, else
    enable GGA on USB at 1 Hz; UBX-RXM-COR exists only on newer
    firmware). Caster etiquette unchanged: GGA upload every 10 s, one
    connection, backoff. Configuration key ids are copied from the
    interface description, not from memory, before coding.
  * app/imu.py GyroSource: the F9rEsfRaw backend listens on the UDP port
    in its own thread, timestamps on arrival, tracks rate and gaps; the
    Lsm6dsl backend stays small (104 Hz ODR, +-500 dps over smbus2) for
    the fallback. Startup bias: 10 s stationary with a variance check
    (abort calibration if the rover moved). Re-trim bias whenever the
    motor target has been zero for 5 s and the gyro variance is low. Yaw
    axis (which of gx, gy, gz is vertical, from the accel reading at
    rest) and GYRO_YAW_SIGN live in nav_params, determined once by
    imu_axes.py. The F9R IMU's axes follow the module's own frame, so the
    sign depends on how the board sits on the rover: measure it.
  * app/heading.py: heading += GYRO_Z_SIGN * gz * dt (compass sense).
    Observations accepted only when speed >= 0.15 m/s, |gyro| <= 15
    deg/s (not turning hard), hAcc <= gate. Two observation types:
    (a) receiver course over ground, weight from headAcc; (b) track
    angle from the displacement over the last >= 0.4 m when hAcc <= 0.1
    m, or >= 1.0 m when FLOAT. Correction gain per observation 0.1..0.3
    (a 1-state Kalman gain on heading with a slow bias state is the
    tidy version; a complementary blend is acceptable for v1). Expose
    heading_valid (False until the first accepted observation) and a
    sigma that grows with time since the last observation.
  * Initial heading: keep the ALIGN creep (straight 0.6..1.0 m) and seed
    from the displacement vector; optional magnetometer seed only if a
    calibration exists (D2). Pingpong legs after the first inherit the
    gyro heading, so only the very first start needs the creep.
  * Tests: sim with 0.05 deg/s residual bias and 1 deg/s noise converges
    within 3 deg in 20 s at FLOAT noise; bench: hand-rotate the rover
    360 deg and the heading returns within 3 deg.

WP2  Controller v2 and missions

  * Keep every v1 gate (hAcc, start radius, pause/fault, cross-track,

    0.15 m/s rising to 1.5 m at 0.4 m/s, plus a small cross-track term so
    the rover converges onto the line instead of running parallel to it.
    Speed schedule: cruise (mission parameter, default 0.25 m/s), reduce
    with heading error and with path curvature at the carrot, minimum
    0.12 m/s, and ramp down over the last 1.5 m. Pivot in place when
    |error| > 60 deg, closed loop on the gyro. Slew limiter 0.5 m/s^2
    and 2 rad/s^2 on the commands (the old motion_profiler idea).
    Commands in physical units (m/s, rad/s) converted with the WP4

  * Mission modes: once | pingpong | loop; loops N or 0 = until STOP.
    Endpoint behavior: stop, pivot to the first bearing of the next leg,

    appended). Per-leg timeout = 3 x (leg length / cruise); mission cap
    is a parameter (default 30 min) instead of the fixed 300 s.
  * Power: nav applies its own speed and pins the follow-source scale to

    and break any speed model.

  * Logging: ~/rover-logs/nav-<timestamp>.csv at 20 Hz with t, state,

  * Review fix: the /ws drive handler drops idle joystick zeros only

    Extend the check to nav.enabled so a stray zero cannot momentarily
    zero a mission's target. The UI sends on press/release only, so the
    risk today is low, but the two autonomy sources should be symmetric.
  * Tick rate: 20 Hz (50 ms) leaves 100 ms of margin to the 150 ms
    watchdog; v1's 10 Hz leaves 50 ms, which a busy Pi can miss and
    stutter the wheels. Keep file and I2C I/O off the control thread.

7. RISKS AND MITIGATIONS
======================================================================

  R1  Gyro path fails. The BerryIMU IS missing (recon), so the plan's
      gyro is the F9R's internal IMU over ESF-RAW. Ways that can fail:
      the message cannot be enabled on this firmware, the rate is too
      low, or the module is not level on the rover (yaw then leaks into
      the other axes; the estimator uses the accel-derived vertical axis
      to pick the yaw component). Fallbacks, in order: remount the
      BerryIMU on the roof (gyro only, magnetometer ignored); a separate
      small IMU board; a second F9P as a moving base for dual-antenna
      heading (about 250 USD, about 0.5 deg from a 1 m baseline, no gyro
      needed). Without any gyro the follower is limited to COG plus
      displacement heading, slower cruise, and reverse-drive turnarounds
      instead of pivots.
  R2  FLOAT-only days: at 0.2 to 0.4 m widen the stop radius to 0.5 m and
      cruise at 0.2 m/s; A3 still holds, A1 may not. At 1 to 2 m (seen
      for 40 minutes on July 19) nothing useful can be driven; T1b is the
      gate, and the fix is on the GPS side (sky view, antenna placement,
      correction age, a converged soak before moving).
  R3  Course-over-ground noise at 0.25 m/s: handled by the displacement
      observation over longer baselines and by the gyro carrying the
      heading between good observations.
  R4  Mecanum slip and lateral drift on grass: closed-loop wheel speed
      helps, the cross-track term corrects, cruise lower on grass; the
      rollers themselves are a reason to keep vy = 0 in autonomy.
  R5  Motor type register reads 0 (WITHOUT_ENCODER): register 51 may be
      open loop in practice, so wheel speed would sag with battery
      voltage and load, and pivots would not repeat. WP0b measures it;
      if type 3 gives a real speed loop, motors.py sets 0x14 and 0x15 at
      startup (one write per power-on) after a polarity check with the
      wheels off the ground.
  R6  Pi load, heat and power: nav at 20 Hz plus a 100 Hz UDP listener is
      light; video and the kiosk are the cost. The recon saw 84.5 C with
      the soft temperature limit active and under-voltage flagged since
      boot. During missions run lean (kiosk off, MJPEG at 6 Hz or the
      H.264 path), watch cpu_temp_c and the live throttle bits in
      telemetry, and verify the 5 V supply can carry Pi 5 + Hailo +
      camera + GPS under motor load (a brown-out that drops the USB GPS
      looks like an RTK loss to nav and ends the mission).
  R7  Wi-Fi loss mid-mission: E-stop needs the link. Mitigation is the
      policy in D3 plus the geofence and mission cap.
  R8  Watchdog gaps: a late nav tick zeroes the wheels for an instant.
      20 Hz tick, I/O off the control thread, and a log of tick jitter.
  R9  Imagery offset when tapping waypoints: tap-to-add is for rough
      planning; MARK with the rover is the accurate source.
  R10 Receiver unknowns: variant and firmware (MON-VER never logged), the
      ESF-RAW sample rate, and whether CFG-SFCORE-USE_SF applies without a
      restart. All are answered by the WP0b bench script in one sitting.
      The robotic-lawn-mower fusion model (receiver-computed heading) is
      recorded as a stretch option only: it needs HPS 1.21 or newer, wheel
      ticks with polarity pushed to the receiver at 10 Hz, user-defined
      mount alignment, and RTK FIXED to calibrate.
  R11 Operator-out-of-loop safety: no physical kill switch is documented
      anywhere (Q10). Claude Rover also reports a past "stale WebSocket"
      failure mode that delayed phone commands by seconds; I could not
      find it in the repo's notes, so treat it as unverified and measure
      STOP latency (phone tap to motor zero) in T0. Onboard backstops
      (geofence, leg timeouts, mission cap, RTK and stall faults) are the
      real mitigation; the phone is a convenience.

9. NUMBERS (known, estimated, to verify)
======================================================================

9.1 Geometry and drivetrain
  Chassis 30 x 24.5 x 10 cm, 1.9 kg, payload 5 kg, spec max 0.6 m/s
  (Chassis specs.pdf). Wheels 97 mm mecanum (radius 0.0485 m).
  Wheel centers: app/kinematics.py uses 0.20 x 0.16 m; the Nov 2025
  rover_lite.py used 0.219 x 0.193 m. [VERIFY with a tape measure.]
  Motor: 520 encoder gear motor, no-load 100 rpm, 11 pole pairs -> 44
  counts per motor rev. Chassis sheet says ratio 1:131; the Hiwonder
  JGB37-520 type says 1:90; the Dec 2025 measurement of 3,845 ticks
  per wheel rev matches 44 x 90 = 3,960 at 97 percent, so 1:90 is the
  likely truth. Top wheel speed about 100 rpm x 0.3047 m = 0.51 m/s.
  Encoders: 12,618.75 ticks per meter (Dec 2025, 1.0 m drive test).

9.2 Command scaling (why NOMINAL_YAW_RATE is optimistic)
  vx = 1.0 -> 0.5 m/s requested -> kinematics (r = 0.04, MAX_RPM 200)
  -> about 60 units. If a unit is 100 ticks/s (pulses per 10 ms), 60
  units = 6,000 ticks/s / 3,845 = 1.56 rev/s = 0.48 m/s, near the
  motor's limit; so "0.5 m/s" is roughly honest by coincidence and
  CRUISE_VX 0.5 is roughly 0.23 m/s.
  omega = 1.0 -> 2.0 rad/s requested -> about 43 units per wheel ->
  0.34 m/s rim speed -> with real half-sums (0.206 m) about 1.65 rad/s
  before slip, less after. nav.py assumes 2.0 rad/s. A 180 deg pivot by
  dead reckoning would stop 20 to 40 percent early. [VERIFY in T2.]

9.3 GPS
  NAV-PVT fields used: lat/lon 1e-7 deg, hAcc mm, gSpeed mm/s, headMot
  1e-5 deg, headAcc 1e-5 deg. Measured solution rate 1.02 Hz (status
  file rewritten at 1.8 Hz). July 19 survey window: FLOAT hAcc 0.08 to
  0.40 m, FIXED 0.02 to 0.03 m, FIXED total 49 s, longest 17 s. July 19
  nav window: FLOAT/NONE at 0.8 to 2.2 m for 40 minutes. Position latency
  today up to 1 s solution + 0.5 s poll + file, about 25 to 35 cm at
  0.25 m/s; at 2 Hz periodic output about 12 cm; at 4 Hz about 6 cm.
  Indoors through the roof (recon): 3D fix, 7 to 10 sats, hAcc 6 to 15 m,
  cog_acc_deg pegged at 180 while parked (course is meaningless at rest,
  as expected).

9.4 Gyro
  F9R internal IMU (part not documented; consumer MEMS class): ESF-RAW
  gyro LSB = 2^-12 deg/s = 0.000244 deg/s, 24-bit signed, so the range is
  +-2048 deg/s; accel LSB = 2^-10 m/s^2. Sample rate fixed by the sensor
  [VERIFY in WP0b, expect of order 100 Hz]. Expect noise of order 0.05 to
  0.1 deg/s rms and a bias of a few tenths of a deg/s before calibration,
  drifting with temperature (the message carries the gyro temperature,
  so a temperature term in the bias model is possible later). Uncorrected
  that is several degrees per minute; with RTK heading corrections every
  few seconds of driving it is irrelevant, and the stationary re-trim
  handles long pauses.
  LSM6DSL fallback: +-500 dps at 17.5 mdps/LSB, about 0.03 deg/s rms at
  50 Hz bandwidth, similar bias behavior.

10. REVIEW NOTES ON app/nav.py v1 (keep, fix, replace)
======================================================================

Keep: phase structure, hAcc gate with per-run override, start-radius
refusal with the "move it to spot 1" message, pause-on-loss with motors
zeroed, cross-track abort, no-progress abort, path-under-field_data
check, lifecycle lock, publish()/finish() pattern, E-stop integration,
forward-only driving, forward-only nearest-point search.

Fix:
  * Heading source (section 5 WP1). The sign conventions in v1 are
    right: desired = atan2(dE, dN) is a compass bearing; positive error
    (carrot clockwise of the nose) -> negative omega (CW); dead reckoning
    subtracts omega x rate x dt. Only the rate constant and the lack of
    a sensor are wrong.
  * Power slider scaling of follow commands (WP2).
  * Mission cap 300 s and single-leg assumption (WP2).
  * 10 Hz tick versus 150 ms watchdog (WP2).
  * xtrack reported as distance to the nearest sample point (up to 0.25
    m of quantization at 0.5 m spacing); compute the perpendicular
    distance to the segment.
  * Arrival uses only distance to the final point; a path that ends in a
    bend can trigger early. Use progress along the path plus distance.
  * No slew limiting: 0 -> cruise in one tick, pivot <-> drive switching
    at 60 deg can chatter. Add hysteresis (pivot above 60, resume drive
    below 35) and the slew limiter.
  * ALIGN creep heads wherever the rover points for up to 3 m, and the
    cross-track abort is suppressed while acquiring but not while
    aligning; with a known initial heading (gyro + seed) the creep can
    be shortened to 0.6 m and aimed.

Replace: _Path with app/paths.py (adds reverse, close, curvature,
perpendicular projection, progress), the single default path with a
path picker, the status dict with mission fields.
